# 租户部署模式 Spec（草案）

> 状态：Draft — 待评审与批准
> 关联需求：`IAM-003`、`IAM-004`、`IAM-009`、`IAM-013`、`PRD-001`
> 决策来源：[访谈 Q520](../product/interview-decisions.md)、[固定租户部署模式 ADR](../adr/2026-10-10-tenant-deployment-modes.md)

## Goal

让部署者在首次启动前选择系统允许一个还是多个租户。模式是数据库级、不可在线切换的部署决策，不是用户可操作的功能开关。

## Tenant modes

配置项为 `roseiot.tenant.mode`，取值 `SINGLE_TENANT` 或 `MULTI_TENANT`，通过 `ROSEIOT_TENANT_MODE` 环境变量或 Spring 配置设置。首次初始化必须显式提供该值；缺失或未知值时启动失败。运行期间不提供 API、管理页面或配置刷新入口修改模式。

两种模式共用相同的数据库结构、用户模型、RBAC、租户资源授权和 MyBatis-Plus 租户隔离插件：

- **`SINGLE_TENANT`**：数据库最多存在一个 `tenant`。`SystemAdmin` 可使用现有创建租户流程建立唯一租户并邀请首位 `TenantAdmin`；创建成功后再次创建必须返回 **409** `single_tenant_limit`。租户用户登录、邀请、成员管理、TenantAdmin 权限和租户资源 API 均正常工作。租户停用/启用和改名语义与多租户模式一致。停用的租户仍计入一个名额。
- **`MULTI_TENANT`**：保持现有契约，SystemAdmin 可创建多个租户；成员、邀请和租户资源按认证主体的租户 ID 隔离。

单租户模式的含义是只有一个租户，不是取消租户上下文，也不是把租户用户降为系统用户。两种模式中的租户数据均不得绕开身份授权或 SQL 租户隔离。

## Durable mode selection

- 数据库使用一条固定配置记录保存首次选择的模式。新增轻量级 `platform_configuration` 单例表，包含固定主键（仅允许一行）、`tenant_mode` 与 `initialized_at`；该表只保存部署元数据，不新增领域实体或面向 API 的资源。
- 第一次应用启动时若配置记录不存在，应用在事务中插入所选模式；如果已有记录，必须精确匹配配置值。不匹配、记录损坏或无法读取时启动失败，应用不得接受业务流量。
- 并发首次启动必须通过数据库唯一约束和原子插入确保只记录一个模式；竞争失败的实例重新读取记录并执行匹配校验。
- 初始化检查在 Web 服务器对外服务前完成；bootstrap CLI 与 Web 模式均校验同一配置，防止先执行 bootstrap 再以不同模式运行。
- 应用不提供更新或删除已存模式记录的代码路径。修改环境变量后重启不能切换模式；数据库恢复必须同时恢复该记录。
- 当前 Spec 不提供 `SINGLE_TENANT` 与 `MULTI_TENANT` 之间的转换，也不自动合并、删除或迁移租户。转换需另行审批迁移 Spec。

## Single-tenant creation invariant

- 在 `SINGLE_TENANT` 中创建租户时，在同一事务内锁定模式配置记录，再检查租户总数并执行现有租户创建和首位管理员邀请流程。
- 租户数量检查包含停用租户。竞争创建请求须串行化，最多一个请求成功；失败请求不得遗留租户或邀请数据。
- `MULTI_TENANT` 不应用单租户数量限制。

## Security and data behavior

- `users.tenant_id` 与 `user_role.scope_tenant_id` 在两种模式下含义不变。登录主体从用户记录确定，客户端不得指定当前租户。
- JWT、会话刷新、租户停用检查和权限修订版本语义不因模式变化而降级。
- `/api/tenants/**` 的 `@PreAuthorize` 规则和资源授权在两种模式保持一致；单租户模式中的系统 API 仍只限系统管理员。单租户模式下不移除租户 Controller、成员管理或邀请 Controller。
- 所有租户拥有的数据表继续执行 SQL 租户隔离；单租户模式不跳过插件或显式资源归属校验。
- 租户状态停用是业务状态，不等于修改部署模式。

## Upgrade and operations

- V3 migration 新建模式记录表但不猜测现有数据库的模式。升级部署必须显式设置 `ROSEIOT_TENANT_MODE`；首次启动将其写入数据库。
- 升级到 `SINGLE_TENANT` 时，若数据库已有超过一个租户（包含已停用租户），应用启动失败并说明需要选择 `MULTI_TENANT` 或执行另行批准的数据迁移；不得静默删除或合并数据。
- 备份和恢复必须包含模式记录。恢复环境的配置与备份中的模式不一致时，应用保持不可用并报告不匹配。
- 日志可以报告当前模式，不得把敏感配置写入日志。

## Acceptance criteria

- **AC-1**：缺少或非法 `roseiot.tenant.mode` 时应用启动失败，不提供服务。
- **AC-2**：首次启动记录所选模式；同一数据库后续以相同模式启动成功，以不同模式启动失败；无 API 或运行时配置刷新可修改模式。
- **AC-3**：并发首次初始化只产生一个模式记录；竞争配置不一致的实例失败关闭。
- **AC-4**：单租户模式允许创建唯一租户及首位管理员邀请；再次创建返回 `409 single_tenant_limit`，包括唯一租户已停用时。
- **AC-5**：单租户模式仍允许该租户成员登录、刷新、管理成员和访问获授权资源；系统用户和租户用户之间仍遵循现有 API 授权边界。
- **AC-6**：多租户模式可创建多个租户；同租户与跨租户数据隔离测试均通过。
- **AC-7**：现有租户停用、会话撤销、RBAC 和租户隔离行为在两种模式下保持正确。
- **AC-8**：从已有数据库首次选择单租户模式时，若有多个租户（包括停用租户）则启动失败且不修改数据。
- **AC-9**：`./mvnw -q verify` 通过。

## Non-goals

- 不提供单租户和多租户模式的在线/重启切换。
- 不删除租户身份、租户用户、租户资源归属字段或租户隔离机制。
- 不提供自动租户合并、拆分、降级或升级迁移工具。
- 不改变租户停用与部署模式的区别。
