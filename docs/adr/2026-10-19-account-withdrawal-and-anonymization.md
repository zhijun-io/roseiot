# 账户注销与个人数据去标识化

- **状态**：Accepted
- **日期**：2026-10-19

## 背景

用户需要停止使用平台并移除个人资料。直接物理删除 User 会破坏会话、邀请和审计记录的外键与追溯关系；仅将账户停用又会保留过多可识别信息。

## 决策

- 用户经近期重新认证并明确确认后，可立即且不可逆地注销自己的账户，不设置等待期或自助恢复期。
- 注销将 User 转为终态 `WITHDRAWN`，立即拒绝后续认证；同一原子用例中撤销全部会话、移除角色关联、删除 UserCredential 与 UserOAuth2Client 关联、清除用户设置及其中的 MFA 秘密，并清除个人资料。需要保留且不可空的邮箱以唯一、不可投递的 `.invalid` 地址替换；已接受邀请记录中可识别用户的目标邮箱也须清除或替换为不可投递占位值。
- 保留不含个人资料的稳定 User ID 和 Tenant 归属，以维持关联关系及历史审计追溯。历史 AuditRecord 保留该不透明 ID，但不得复制姓名、邮箱、凭证或其他个人资料；审计记录按独立保留策略管理。
- 注销不得移除最后一名有效 `SYSTEM_ADMIN`，也不得移除 `ACTIVE` 客户租户最后一名有效 `TENANT_ADMIN`。已注销账户不可重新启用；原邮箱以后可作为新身份重新邀请。
- 具体 API、允许保留的审计字段及审计保留期限由阶段 1 Spec/Plan 定义，且不得削弱上述最小化与管理员不变量。

## 后果

- User 需要支持不可逆终态；凭证和用户设置在注销流程中必须能被可靠清除，且并发角色变更不能绕过最后管理员保护。
- 注销操作和清理必须有事务边界、可验证的副作用及审计记录，同时不得将已清除的个人资料复制到日志或审计事件。
- 保留 opaque User ID 可维持历史记录关联，但不等同于物理删除 User 记录。
