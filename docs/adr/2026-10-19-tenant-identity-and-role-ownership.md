# 用户租户归属与角色归属

- **状态**：Accepted
- **日期**：2026-10-19

## 背景

Roseiot 需要同时支持平台管理身份和客户租户成员。若用户可在多个租户间切换，认证主体、数据归属和授权边界会显著复杂化；若用角色名称区分管理员，也会使重命名影响授权。

## 决策

- 每个 `User` 必须且只属于一个 `Tenant`。平台用户属于保留的 `default` tenant；该租户不是普通客户租户。
- 用户可以没有角色，也可以拥有多个所属租户内的角色。用户没有角色时仍可登录，只能访问 `/api/me/**` 和明确开放的公开接口。
- 每个 `Role` 只属于一个租户。`default` tenant 只承载系统角色；普通租户只承载租户角色。
- `SYSTEM_ADMIN` 和 `TENANT_ADMIN` 是受保护的内置角色，分别为 `default` tenant 和每个客户租户初始化。两者的记录、名称、状态及权限关联均不可由管理 API 修改、停用或删除；普通角色仍可由相应管理者维护。客户租户初始化流程见[租户开通与启用](2026-10-19-tenant-provisioning-and-activation.md)。
- 角色显示名称可修改，不参与授权判断。授权由角色关联的权限标识决定，权限标识采用 `模块:资源:动作` 格式；用户多个有效角色的权限取并集。租户数据操作仍需校验用户与目标租户的归属关系。
- 客户租户用户的目标租户由其所属租户确定；系统管理员可在具备对应权限标识时通过目标租户 ID 定位租户管理资源。无论何种情况，租户 ID 本身都不是授权依据，系统身份也不自动授予客户业务数据访问权。
- 需要始终至少保留一名有效系统管理员及每个 `ACTIVE` 客户租户至少一名有效租户管理员。系统管理员按其是否属于 `default` tenant 且关联受保护的 `SYSTEM_ADMIN` 角色识别；租户管理员按其是否关联所属租户受保护的 `TENANT_ADMIN` 角色识别。删除、注销、停用账户或移除其管理员角色均不得移除最后一名对应管理员；并发状态变更也必须维护此不变量。

## 后果

- 用户、角色和租户关系可由外键及服务端授权检查明确验证。
- 平台管理权限与客户租户业务数据权限相互独立。
- 跨租户用户身份、用户租户迁移和跨租户角色分配不在当前模型内；如有需求，需另行评估并修订本决策。
- 邀请可不分配角色，因此邀请接受流程不能假设新用户必然具有管理权限。
- 待启用租户若首位管理员邀请过期或被撤销，可保持 `PENDING_SETUP`，由系统管理员重新发送邀请或取消租户；具体接口及失败恢复流程由管理模块 Spec 规定。
