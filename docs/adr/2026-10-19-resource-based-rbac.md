# 基于分层资源目录的 RBAC

- **状态**：Accepted
- **日期**：2026-10-19

## 背景

平台需要同时组织管理端导航并授权服务端操作。菜单的可见性与 API 授权有关联，但二者不能混为一谈；授权也不能依赖前端隐藏按钮或角色名称。

## 决策

- 统一资源目录使用 `GROUP`、`MENU`、`BUTTON` 三种类型；Resource 不设置权限范围字段。
- 资源层级为 `GROUP → MENU → BUTTON`。只有 `MENU` 可以配置路由地址；`GROUP` 和 `BUTTON` 不设置路由地址。
- `GROUP` 和 `MENU` 只组织导航，不直接授权 API。`BUTTON` 是可授权操作资源，具有稳定、必填的权限标识；API 服务端检查对应权限标识。菜单可见性可根据已授予的 BUTTON 及其祖先菜单推导，父资源不隐式授予子资源权限。
- 每个受保护 API 操作必须声明相应权限标识，格式为 `模块:资源:动作`。只有当前用户有效角色中关联了该标识，服务端才允许操作；权限标识之外仍须执行身份状态和数据归属校验。
- 角色通过 `role_resource` 关联 BUTTON 资源。`tenant_resource` 限定客户租户可用的 BUTTON 资源；租户角色不得关联未获准资源，但该关联本身不授予用户操作权限。
- 客户租户用户访问租户数据时，目标租户必须与用户所属租户一致。系统管理员属于 `default` tenant，可在具备相应权限标识时管理指定客户租户的租户管理资源；目标 tenant ID 只用于定位资源，不能替代权限检查，也不因此获得该租户业务数据访问权。
- 平台和租户管理 API 按资源归属使用 REST 路径；请求不得直接传入权限标识以绕过角色授权。具体路径和 HTTP 契约由模块 Spec 定义。

## 后果

- 前端展示资源与服务端授权有共同目录，但服务端始终独立执行授权检查。
- 资源树结构变化不会自动扩大权限。
- 导航资源、权限标识和 API 操作映射需要一致性校验；具体字段约束、错误响应及端点由阶段 Spec 维护。
