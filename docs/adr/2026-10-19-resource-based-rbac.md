# 基于分层资源目录的 RBAC

- **状态**：Accepted
- **日期**：2026-10-19

## 背景

平台需要同时组织管理端导航并授权服务端操作。菜单的可见性与 API 授权有关联，但二者不能混为一谈；授权也不能依赖前端隐藏按钮或角色名称。

## 决策

- 统一资源目录使用 `GROUP`、`MENU`、`BUTTON` 三种类型，并带有 `PLATFORM` 或 `TENANT` scope。
- 资源层级为 `GROUP → MENU → BUTTON`，父子资源必须属于相同 scope。只有 `MENU` 可以配置路由地址；`GROUP` 和 `BUTTON` 不设置路由地址。
- `GROUP` 和 `MENU` 只组织导航，不直接授权 API。`BUTTON` 是可授权操作资源，具有稳定、必填的权限标识；API 服务端检查对应权限标识。菜单可见性可根据已授予的 BUTTON 及其祖先菜单推导，父资源不隐式授予子资源权限。
- 每个管理 API 操作必须声明相应 scope 的权限标识。只有当前用户有效角色中关联了该标识，服务端才允许操作；平台用户管理租户也必须具备对应的 `PLATFORM` 权限。
- 角色仅关联同 scope 的 BUTTON 资源。`tenant_resource` 限定普通租户可用的 TENANT BUTTON 集合，租户角色不得超出该集合。
- 平台和租户管理 API 按资源归属使用 REST 路径；请求不得直接传入资源或权限标识以绕过角色授权。具体路径和 HTTP 契约由模块 Spec 定义。

## 后果

- 前端展示资源与服务端授权有共同目录，但服务端始终独立执行授权检查。
- 资源树结构变化不会自动扩大权限。
- 导航资源、权限标识和 API 操作映射需要一致性校验；具体字段约束、错误响应及端点由阶段 Spec 维护。
