## 四、核心原则

请严格遵守以下原则：

1. 性能优先，其次是成本、复杂度和形式感。
2. 最小改动、最小依赖、最小抽象。
3. 优先使用 Java、Spring Boot 和已有项目能力，不为展示技术而引入技术。
4. 遵循 Unix 哲学，保持模块职责单一，优先组合简单组件。
5. 避免过度设计。不要为“未来可能使用”提前引入微服务、Kubernetes、复杂事件总线、通用 DSL 或重量级规则引擎。
6. 先做垂直切片：一个可用的业务闭环比一批互不连通的空壳模块更重要。
7. 每次迭代后项目必须能够编译、启动并通过与本次范围匹配的测试。
8. 发现需求、设计或实现中的问题时直接指出，并解释影响，不要为了迎合我而默认同意。
9. 默认进行对抗式审核，主动检查性能、并发、安全、数据一致性、故障恢复、兼容性和可维护性风险。
10. 所有设计都要说明当前阶段解决什么问题、明确不解决什么问题，以及未来如何演进。

## 五、Spec 驱动开发和交付流程

roseiot 使用 Spec-Driven Development（SDD）作为长期迭代的默认工作方式。可以使用 `sdd-spec`、`sdd-plan`、`sdd-build` 和 `sdd-review` 技能，但必须遵守以下交付门禁：

1. 有明确行为变化、持久化变化、安全边界、公开 API、消息协议、跨模块依赖或基础设施变化时，先编写 Spec，不直接写代码。
2. Spec 至少包含目标、范围、非目标、仓库事实、需求、约束、风险和可验证的 `AC-n` 验收标准。每个需要交付的行为都必须映射到一个或多个 `AC-n`。
3. Spec 必须得到我明确确认后，才能进入 Plan。文件存在不等于我已批准。
4. Plan 必须读取已批准的 Spec，并把所有 `AC-n` 拆成可独立验证的垂直切片。每个切片都要包含依赖、失败测试或其他可重复证明、实现范围、验证命令和完成条件。
5. Plan 必须得到我明确确认后，才能进入 Build。不要先写一批基础设施代码，再用 Spec 追认范围。
6. Build 按切片执行 RED → GREEN → REFACTOR：行为代码先写能正确失败的测试，再做最小实现，最后重构并保持测试绿色；无法合理自动化测试的文档、配置或生成工作必须提供确定、可重复的替代证明。
7. 如果实现中发现需要改变 `AC-n`、公开行为、数据模型、安全边界或切片边界，停止当前实现，回到 Spec 或 Plan 阶段，不得静默扩大范围。
8. Spec 的验收标准或约束发生变化时，更新原 Spec 并记录修订原因、受影响的 `AC-n` 和 Plan 影响；不要创建含糊的 `-v2` 副本。
9. 重要阶段完成后，可使用 `sdd-review` 做 Standards 和 Spec 两个维度的独立审查。审查结果必须区分标准问题、规格缺口、范围蔓延和实现错误，不把两个维度混成一份结论。
10. Spec、Plan、Build 和 Review 的输出使用中文，保留 `AC-n`、命令、路径和技能 ID 等技术字面量。

默认文档位置：

- `docs/sdd/00N-<topic>-spec.md`
- `docs/sdd/00N-<topic>-plan.md`

每个阶段都必须能从 Spec 的 `AC-n` 追踪到 Plan 切片、测试或证明、实现和最终验证结果。

## 六、明确架构和技术约束

### 6.1 单体架构和多实例部署

roseiot 当前采用模块化单体架构，不采用微服务拆分作为初始目标，但必须支持同一个应用的多实例部署。

- 业务模块在同一个 Spring Boot 进程中运行，通过清晰的领域边界和依赖规则隔离。
- 应用实例必须尽量无状态，可以在负载均衡后水平扩展。
- 不把登录会话、设备在线状态、WebSocket 连接元数据、任务锁或业务状态只保存在单个实例的内存中。
- 本地文件系统只用于临时文件或明确声明的缓存，不作为跨实例共享存储。
- 需要共享的数据放入 PostgreSQL 或明确选择的外部基础设施；需要分布式锁、幂等或选主时，说明一致性和故障语义。
- 定时任务、数据库迁移、消息消费和设备连接等多实例场景必须说明是否允许每个实例执行、是否需要选主、分片或幂等保护。
- 使用 Docker Compose 至少验证两个应用实例连接同一套基础设施时的启动、访问和关键业务行为。
- 不要为了“支持多实例”直接引入 Kubernetes、服务网格或分布式事务；先用简单可验证的方案解决问题。

### 6.2 模块化、Maven 模块和领域边界

使用按领域组织的模块化单体，而不是按 Controller、Service、Mapper 进行全局分层堆放。领域能力使用 Maven module 组织，协议适配和基础设施按技术能力单独组织。领域模块的划分不能过细，默认以“未来是否具备独立部署为微服务的条件”作为主要判断标准，不能按实体、数据库表或单个功能机械拆分。

- 根 Maven 项目负责聚合、版本、插件和依赖管理；启动模块负责 Spring Boot 启动和运行时装配；每个领域模块负责一个完整业务能力；基础设施模块负责无业务归属的技术能力和协议适配。
- 每个领域 Maven 模块拥有自己的领域模型、领域服务、应用用例、仓储接口、数据持久化实现、输入输出边界和对外可见 API；内部实现不得被其他模块直接引用。
- 领域模型和领域服务原则上不依赖 Spring Boot Starter、数据库驱动或具体协议；领域模块中的 `persistence/` 可以依赖 MyBatis Plus 和 PostgreSQL，但必须与领域核心隔离并由 ArchUnit 保护。
- 模块之间通过明确的用例、接口、领域事件或稳定 DTO 交互，不直接访问其他模块的数据库表、Mapper 或内部实现。
- Controller、MQTT、WebSocket 和 gRPC 只是适配器，不把协议对象传入领域核心。
- 依赖方向要从启动模块指向领域和基础设施；基础设施不得反向依赖任何领域模块。领域模块只能依赖基础设施公开的、与业务无关的技术契约，领域核心不得依赖 Web、MQTT、gRPC Runtime、MyBatis Plus 或 PostgreSQL API。
- 跨模块调用必须能说明调用方、被调用方、事务边界、失败语义和是否允许同步耦合。
- 只有同时具备相对完整的业务闭环、清晰的数据所有权、稳定的外部契约、可独立测试和未来独立部署价值时，才新增领域 Maven module。
- 如果一个能力必须频繁同步调用另一个领域、共享同一事务或共享大量内部数据，默认先作为现有领域模块中的子域或子包，不单独拆 module。
- 判断模块是否值得拆分时，至少评估：独立部署收益、独立扩缩容需求、故障隔离价值、数据边界、团队或迭代独立性、跨模块通信成本和运维成本。
- `shared` 或 `common` 模块只能放少量稳定、无业务归属的基础类型；禁止把业务对象、数据库工具和所有无法归类的代码塞进公共模块。
- 以高内聚、低耦合为目标：模块内部围绕一个清晰业务能力组织数据和行为，模块之间只暴露完成用例所需的最小契约。
- 抽象优先放在变化频繁或替换成本高的边界，例如持久化、消息、协议和外部服务；稳定且只有一个实现的内部逻辑不提前抽象。
- 可扩展性必须通过新增实现、配置或模块完成，而不是通过大量空接口、继承层级、万能工厂或反射注册表实现。

推荐的初始模块拓扑如下。第一阶段只创建当前 Spec 需要的模块，后续只有在满足独立部署判断标准时才增加领域模块，不创建空模块：

```text
roseiot/                         # 根聚合项目，packaging=pom
├── roseiot-server/              # 唯一可执行 Spring Boot 应用和运行时装配
├── roseiot-infrastructure/      # 基础设施和技术适配器
├── roseiot-tests/               # 架构、跨模块集成和端到端测试
├── roseiot-identity/            # 用户、租户、角色、权限和认证用例
├── roseiot-device/              # 产品、设备、凭证和生命周期用例
├── roseiot-notice/               # 通知编排、通知模板、通知记录和通知持久化
└── roseiot-starter-*/           # 已验证可复用后的独立 Starter
```

初始候选领域模块优先控制在以下范围：

- `roseiot-identity`：用户、租户、客户、角色、权限和认证。
- `roseiot-device`：产品、设备、凭证、设备状态、遥测、事件、告警和基础规则。除非后续证明具备独立部署价值，否则这些能力先作为 `roseiot-device` 内的子域或子包。
- `roseiot-notice`：通知编排、模板、通知记录、发送状态和通知持久化。该模块保留为独立候选，是因为通知能力可能拥有独立的通道、重试、限流和扩缩容需求；是否最终独立部署仍需通过实际场景验证。

不要因为出现 `alarm`、`rule`、`telemetry`、`realtime` 等名词就自动创建对应 Maven module。`realtime` 通常属于协议适配能力，默认放在 `roseiot-infrastructure`；其他能力先放入最接近的领域模块。

依赖方向固定为：

```text
roseiot-server
  ├── roseiot-*
  └── roseiot-infrastructure

roseiot-* 领域模块 ──> roseiot-infrastructure 的公开技术契约（可选）
roseiot-infrastructure -X-> roseiot-* 领域模块
roseiot-tests ──> server、infrastructure、roseiot-*（测试依赖）
roseiot-starter-* ──> 对应 infrastructure 能力
domain model ──> JDK only; application layer may use minimal Spring Core/Transaction APIs
roseiot-* 领域核心 -X-> MyBatis Plus / JPA / PostgreSQL / HTTP / MQTT / gRPC Runtime
```

- `roseiot-server` 是唯一负责组装具体实现和启动应用的模块；领域模块和 `roseiot-infrastructure` 不得反向依赖 `roseiot-server`。
- `roseiot-infrastructure` 初期作为一个 Maven module，内部按能力隔离：`database/`、`mqtt/`、`grpc/`、`websocket/`、`messaging/`、`notification/`、`observability/` 和 `configuration/`。它不包含任何领域仓储、领域服务或业务规则；当其规模或复用边界足够明确时，再拆成多个 infrastructure module。
- `roseiot-tests` 只承载 ArchUnit、跨模块集成、多实例和端到端测试；领域模块和基础设施模块的单元测试、组件测试保留在各自的 `src/test` 中。
- 领域模块内部同时放领域模型、领域服务、应用用例、仓储接口和持久化实现；不要把所有端口集中到一个万能 `infrastructure-core` 模块。
- gRPC 的 Protobuf 契约、生成代码和 Server/Client 适配器初期放在 `roseiot-infrastructure/grpc/`，不得进入领域模型；只有需要独立版本管理或供外部项目复用时，才拆出独立契约 module。
- MyBatis Plus、PostgreSQL 和未来 JPA 实现放在各领域模块自己的 `persistence/` 下；MQTT、WebSocket、消息队列、通知通道和通用数据库能力放在 `roseiot-infrastructure` 内按能力隔离。
- `roseiot-notice` 负责通知编排、模板、记录、状态和持久化；它可以依赖 `roseiot-infrastructure` 暴露的技术无关通知通道契约。`roseiot-infrastructure/notification/` 只负责邮件、短信、站内信或第三方通知通道等技术实现，不依赖 `roseiot-notice`。
- 未来替换 JPA 时，在对应领域模块内新增或替换 `persistence/jpa/` 实现，复用该领域的仓储接口、领域服务和测试；不要求 MyBatis Plus 和 JPA 并存。
- `roseiot-tests` 依赖需要检查的模块，仅用于测试，不得被生产模块依赖；ArchUnit 规则必须同时验证 Maven 模块依赖和模块内部包边界。
- 只有存在真实领域职责、稳定依赖边界和未来独立部署价值时才新增领域模块；不要创建空模块、重复 DTO 模块或为了未来可能拆分而复制接口。

### 6.3 持久化和 MyBatis Plus 可替换性

生产实现当前使用 PostgreSQL 和 MyBatis Plus。每个领域模块可以拥有自己的持久化实现，但领域模型和领域服务必须保留将来替换为 JPA 的可能性。

- MyBatis Plus 只能位于领域模块的 `persistence/mybatis/` 或明确的持久化适配器包中；不得进入领域模型、领域服务和应用用例核心。
- 领域对象、领域服务和应用服务不得依赖 `BaseMapper`、`IService`、Wrapper、MyBatis 注解、分页对象或其他 MyBatis Plus 类型。
- 通过领域仓储接口、查询端口或持久化 DTO 隔离领域核心与 ORM 实现；不要为了抽象而建立没有真实调用方的通用仓储框架。
- 数据库实体、领域对象和 API DTO 默认分离，映射逻辑放在适配器边界。
- 未来替换为 JPA 时，应能在对应领域模块新增或替换 `persistence/jpa/`，复用领域模型、领域服务、应用用例和仓储接口；不要求同时支持两种 ORM，也不提前引入 JPA。
- 任何无法避免的 MyBatis Plus 特性都必须记录在技术决策中，并说明替换成本。
- 数据库结构使用 PostgreSQL 特性时，说明是否影响未来数据库迁移；不要为了抽象数据库而放弃 PostgreSQL 的必要能力。

### 6.4 ArchUnit 架构约束

使用 ArchUnit 将模块边界和依赖方向变成自动化测试，而不是只写在文档中。

- 为领域模块、应用层、适配器层和基础设施层定义可执行的包依赖规则。
- 至少验证：领域模型、领域服务和应用用例不依赖 Web、MyBatis Plus、JPA、gRPC 和具体数据库；领域模块的持久化包只能被本领域允许的应用边界使用；基础设施模块不依赖任何领域模块；模块之间不访问彼此的内部包。
- ArchUnit 测试必须接入 Maven 验证流程，并在新增模块或边界变化时同步更新。
- 规则保持少而有价值，避免编写只验证包名、无法阻止真实耦合的形式化规则。
- 如果规则与现有实现冲突，先修正边界或记录明确的例外，不使用大量 `ignore` 掩盖问题。

### 6.5 gRPC 调用

项目需要支持 gRPC 调用，但 gRPC 不是引入微服务的理由。初期可以在单体中同时提供 gRPC Server 和 gRPC Client 适配能力，用于外部系统调用、内部明确的跨模块边界验证或未来拆分准备。

- 使用 Protobuf 定义稳定的服务契约、请求、响应、错误和版本演进规则。
- gRPC Server 只负责协议映射、认证和请求边界校验，业务逻辑复用应用用例，不复制一套业务实现。
- gRPC Client 通过端口或适配器隔离，领域核心不得依赖生成的 Stub 或 gRPC Channel。
- 明确 deadline、取消、重试、幂等、最大消息大小、连接复用、错误码和兼容策略。
- 多实例部署时说明 gRPC 的目标地址、负载均衡、服务发现或外部代理方案；初期优先使用 Docker Compose 服务名或明确配置，不提前引入复杂服务发现。
- 生产或跨网络调用应评估 TLS、认证、授权和敏感数据保护；本地开发可以使用明确的非 TLS 配置，但不得把它默认当成生产方案。
- 为 gRPC Server 和 Client 添加至少一条可运行的协议集成测试。

### 6.6 Docker Compose 和 PostgreSQL

使用 Docker Compose 搭建本地基础设施，数据库固定使用 PostgreSQL。

- Compose 文件只编排本地开发和集成测试所需的基础设施，不把所有应用逻辑塞进 Compose 配置。
- PostgreSQL 使用明确的版本、健康检查、持久化卷、非敏感环境变量和最小权限账号。
- 应用支持通过环境变量或配置文件连接 PostgreSQL，不把本地凭证写入源码。
- 数据库迁移必须可重复执行、版本单调递增，并在多实例启动时避免重复或并发执行造成破坏。
- 后续引入 Redis、MQTT Broker、消息队列等设施时，先证明当前阶段确有需要，并在 Compose 中分别说明用途、资源成本和关闭方式。
- 至少提供单实例和多实例的本地启动方式，以及 PostgreSQL 健康检查和初始化说明。

### 6.7 基础设施独立化和 Spring Boot Starter

底层基础设施代码必须与业务代码低耦合，并以将来能够封装为独立 Spring Boot Starter 为设计目标。Starter 化是边界约束和复用能力，不是当前阶段必须发布到公共仓库的工作。

- 基础设施按能力拆分，例如数据库通用能力、审计、缓存、消息、gRPC、WebSocket、通知和可观测性；每个能力定义清晰的配置、SPI、生命周期和失败语义。领域专属持久化仍归属对应领域模块。
- 业务模块可以依赖基础设施公开的、与业务无关的技术契约，但不依赖基础设施实现类、驱动、连接对象、自动配置类或 Starter 私有配置。
- 基础设施模块可以依赖具体技术，例如 PostgreSQL Driver、MQTT Client、邮件客户端或 gRPC Runtime；它不得导入、实现或扫描任何领域模块的类。
- Starter 模块只负责自动配置、条件装配、配置属性、默认实现、健康检查和必要的运行时集成，不包含用户、设备等业务规则。
- Starter 必须支持显式关闭、替换默认 Bean、配置覆盖和合理的缺省行为；不能在引入依赖后偷偷创建连接、线程、表或后台任务而不提供配置说明。
- Starter 的自动配置测试必须验证启用、禁用、缺少可选依赖、配置覆盖和多实例运行时行为。
- 基础设施模块应能在没有具体业务模块的情况下进行单独测试和启动验证；需要业务上下文时，使用最小测试 Fixture，不把业务模块作为基础设施测试的必需依赖。
- 不要为了“可 Starter 化”提前制造十几层抽象。只有跨模块稳定、存在至少一个真实实现或明确复用场景的边界才抽取接口。

### 6.8 API、消息和协议契约

- HTTP API 使用 OpenAPI 或等价方式维护可阅读、可验证的契约；统一错误响应、错误码、分页、排序、时间格式、请求 ID 和幂等语义。
- 公开 API、MQTT Payload、WebSocket 消息和 gRPC Protobuf 都必须定义版本演进和向后兼容策略。
- 对会产生副作用的 HTTP、MQTT 和 gRPC 操作定义幂等键、重复请求行为、超时和错误恢复语义。
- DTO、领域对象、持久化对象和消息对象默认分离；映射必须显式可测试，不使用隐式转换掩盖边界。
- API 变更必须说明兼容窗口、迁移方式和删除旧版本的条件，不维护没有实际调用方的兼容别名。

### 6.9 PostgreSQL、迁移和并发控制

- 使用 Flyway 或经确认的等价迁移工具；迁移版本单调递增、可重复执行，不依赖手工修改生产数据库。
- 领域模块拥有本领域表结构、索引、约束和迁移文件；`roseiot-infrastructure` 只提供数据源、事务、迁移运行和通用数据库能力，不拥有业务表。
- 每个事务必须说明边界、隔离级别、失败回滚行为和跨模块影响。
- 根据业务场景选择唯一约束、乐观锁、悲观锁、数据库原子操作或分布式锁；不把并发安全寄托在应用实例内存中。
- 对分页、批量写入、慢查询、连接池、索引和数据保留策略提供可验证的设计或基准结果。

### 6.10 安全边界

- 管理用户认证、设备认证、服务间认证和 WebSocket 连接认证分别定义身份来源、权限模型和 Token 生命周期。
- 明确 JWT/Refresh Token 的过期、吊销、密钥轮换和多实例共享策略；设备凭证支持生成、轮换、禁用和安全存储。
- 所有 HTTP、MQTT、WebSocket 和 gRPC 输入都要校验大小、格式、权限、租户和资源作用域。
- 对登录、设备连接、命令下发、消息发布和高成本查询设计限流、超时和消息大小限制。
- 密钥、Token、Webhook、连接串和第三方凭证只从环境变量或未跟踪配置读取；日志、异常、测试报告和演示数据必须脱敏。

### 6.11 分布式可靠性和多实例语义

- 默认按至少一次投递和可能重复执行设计；业务处理必须通过幂等键、唯一约束或 Inbox 等机制安全处理重复消息。
- 需要保证数据库变更与消息发布一致时，评估 Outbox；需要消费去重时，评估 Inbox，不声称不存在证据的 Exactly Once。
- 重试必须有最大次数、退避、超时和死信策略；不可重试错误不得无限重试。
- 定时任务、数据库迁移、消息消费、MQTT 下行命令和 WebSocket 推送必须定义多实例下的执行者、路由、故障转移和恢复方式。
- 设备连接、设备状态和 WebSocket 连接不能只保存在单实例内存；必须说明共享状态、连接路由、跨实例广播和背压方案。
- 需要熔断、降级或隔离时，先通过故障场景证明需求，再选择最小实现。

### 6.12 可观测性

- 使用结构化日志，并统一 Request ID、Trace ID、Message ID、Device ID 和 Tenant ID 的关联规则；敏感字段不得进入日志。
- 提供健康检查、就绪检查和关键依赖状态检查；健康检查不得把短暂业务失败误报为进程存活失败。
- 使用 Micrometer 和必要的 OpenTelemetry 能力观测请求延迟、错误率、MQTT 连接数、消息吞吐、消费延迟、重试、死信、数据库连接池和 WebSocket 连接。
- 每个性能结论必须记录测试场景、数据规模、硬件或容器资源、吞吐、延迟、错误率和瓶颈；没有实测数据不得声称高性能或高并发。

### 6.13 测试和质量门禁

- 领域规则使用单元测试；数据库、HTTP、MQTT、WebSocket、gRPC 和消息队列使用集成测试或协议测试。
- PostgreSQL、Redis、MQTT Broker、消息队列等真实依赖优先使用 Testcontainers 或 Docker Compose 验证，避免大量 Mock 替代集成边界。
- `roseiot-tests` 负责 ArchUnit、跨模块、双实例、契约和端到端测试；各领域模块和基础设施模块保留本地快速测试。
- 为重复消息、乱序消息、超时、断线重连、权限越界、跨租户访问、实例故障和重试耗尽提供失败场景测试。
- Maven `verify` 是统一质量入口；格式、编译、单元测试、集成测试、ArchUnit 和必要的静态检查必须在文档中有可复现命令。

### 6.14 IoT 数据和设备语义

- 明确设备在线/离线判定、心跳、保活、遗嘱消息和服务端时间与设备时间的可信边界。
- 遥测处理必须定义重复、乱序、迟到、缺失、非法类型和异常时间戳的行为。
- MQTT 明确 QoS、Topic 权限、Payload 大小、消息版本、保留消息和离线消息策略；不默认承诺消息顺序或 Exactly Once。
- 设备命令必须具备请求 ID、响应关联、超时、重试、取消和设备离线时的处理语义。
- 明确热数据、历史数据、归档、保留期限、删除和查询范围；不要仅因物联网场景默认引入时序数据库。

### 6.15 技术引入规则

- 引入 Redis、消息队列、调度平台、服务发现、时序数据库、搜索引擎、Kubernetes 或服务网格前，必须先说明当前问题、替代方案、资源成本、运维成本、验证方式和移除成本。
- 技术名称不作为阶段验收标准；可运行行为、故障语义、测试证据和性能数据才是验收标准。
- 优先使用 Spring Boot、Java 和 PostgreSQL 已有能力；第三方依赖只在带来明确收益时引入。

## 七、简历项目要求

roseiot 必须逐步形成可用于面试的项目证据。每个重要阶段都要留下以下内容：

- 一条可运行的端到端链路，例如设备认证、MQTT 上报、异步处理、存储、规则判断、告警和 WebSocket 推送。
- 关键技术决策、备选方案、取舍、限制和迁移路径。

- 性能证据：测试场景、数据规模、吞吐、延迟、资源消耗和瓶颈。没有实际测量时，不得声称“高性能”或“高并发”。
- 可观测性证据：日志、指标、健康检查、请求或消息关联信息。
- 可复现的启动命令、测试命令、演示脚本和必要的样例数据。
- 一份适合面试讲解的技术总结，包含背景、难点、方案、结果、失败尝试和后续改进。

不要虚构用户规模、设备数量、吞吐量、可用性百分比或生产成果。简历中的量化数据必须来自可复现的测试或明确标注为本地基准结果。

## 九、建议的目录和边界

初始目录可以采用以下结构，但不要机械照搬：

```text
roseiot/
├── pom.xml
├── README.md
├── AGENTS.md
├── docs/
├── roseiot-server/
│   ├── src/main/java/
│   ├── src/main/resources/
│   └── src/test/
├── roseiot-infrastructure/
│   └── src/
├── roseiot-tests/
│   └── src/test/
├── roseiot-<domain>/
│   └── src/
└── ui/
```

后端保持模块化单体应用，按领域边界和技术适配边界组织 Maven module，并支持通过 Docker Compose 启动多个应用实例。根项目只做 Maven 聚合和统一管理，不包含业务源码；`roseiot-server` 是唯一可执行应用。

不要一开始创建大量空模块、空包、空接口、Base 类、Util 类、Manager 类或通用框架层。领域模块在对应 Spec 进入实现阶段时创建，并且首个提交必须带来可验证的业务行为或边界测试。

推荐逐步形成的边界包括：

- identity：用户、租户、角色、权限和认证
- device：产品、设备、凭证、生命周期、遥测、事件、告警和基础规则；后四者默认作为 device 内部子域
- notice：通知编排、模板、发送记录、状态和持久化
- transport：MQTT、HTTP、WebSocket、gRPC 等协议适配，属于基础设施能力
- messaging：消息队列、重试、死信和消费幂等，属于基础设施能力
- infrastructure：基础设施能力的实现和配置；不作为承载所有代码的万能模块

以上只是候选边界。只有在出现真实业务职责时才建立对应模块。

## 十、阶段路线

每个阶段必须包含：目标、范围、领域模型、数据模型、API 或消息协议、安全要求、测试计划、验收标准、简历价值、风险和后续扩展点。

### 阶段 0：项目基础

- 创建 Maven 项目并验证 Java 和 Spring Boot 版本。
- 建立最小目录结构、配置管理、日志、统一错误响应和健康检查。
- 创建根聚合 POM、`roseiot-server`、`roseiot-infrastructure` 和 `roseiot-tests`；领域模块只在对应垂直切片开始时创建。
- 建立 README、架构文档、路线图、决策记录和开发说明。
- 建立 `docs/sdd/` 目录并起草阶段 0 Spec；Spec 获得批准后再拆分 Plan，阶段 0 的实现也必须遵循批准门禁。
- 增加 Docker Compose 和 PostgreSQL 的最小本地基础设施配置；暂不引入 MQTT Broker、消息队列、Redis 等非必要组件。
- 建立最小 Maven 模块边界和 ArchUnit 架构测试，验证根项目、启动模块、基础设施模块、测试模块和领域模块的依赖方向。
- 预留 gRPC 的契约和适配器边界；只有阶段目标需要时才实现具体服务。
- 明确基础设施公开契约、实现模块和应用组装模块的依赖方向，验证领域模型、领域服务和应用核心不直接依赖 MyBatis Plus 或其他基础设施实现。
- 添加最小但有价值的单元测试和应用启动测试。
- 通过 Maven 编译、测试和必要的静态检查。

验收标准：项目可以编译、启动，有健康检查接口，有可运行测试；根 POM 可以聚合 `roseiot-server`、`roseiot-infrastructure` 和 `roseiot-tests`；Docker Compose 可以启动 PostgreSQL；ArchUnit 测试接入 Maven 验证流程并能阻止非法模块依赖；应用至少能以两个实例连接同一 PostgreSQL 启动。除 PostgreSQL 外，不提前引入 MQTT Broker、消息队列等暂时不用的基础设施。

### 阶段 1：身份、认证和授权

- 用户、租户、客户、角色和权限。
- 登录、密码安全存储和接口保护。
- 选择 JWT 或 Session，并说明选择理由。
- 明确未登录、无权限、资源不存在和跨租户访问的错误语义。
- 添加审计信息和最小数据隔离机制。

持久化实现使用 MyBatis Plus，但必须通过仓储或查询端口隔离；阶段验收中增加 PostgreSQL 集成测试和跨实例访问验证。

重点验证密码哈希、Token 生命周期、权限边界、越权访问、敏感信息脱敏和并发更新。

### 阶段 2：产品和设备管理

- 产品、设备、设备凭证、设备状态和设备生命周期。
- 设备创建、查询、更新、禁用、注销和分页。
- 明确产品与设备关系、设备唯一标识、凭证存储和不可变字段。
- 对并发修改、删除语义和租户隔离进行测试。

设备在线状态和其他跨实例状态不得只保存在单个应用实例内存中。

### 阶段 3：MQTT 设备接入

- 对接选定的 MQTT Broker 或 MQTT 服务端组件。
- 处理设备连接、断开、认证、上行消息和下行命令。
- 设计 Topic、Payload、版本、错误响应和 QoS 策略。
- 处理重复消息、消息顺序、离线设备、重试和幂等。

先做一个可演示的设备生命周期闭环，再扩展协议能力。必须解释 MQTT 客户端或 Broker 的选择，以及高并发场景的连接、线程、内存和背压风险。

多实例部署时必须明确设备连接由哪个实例持有、下行命令如何路由到正确实例、状态如何共享，以及实例故障后的恢复方式。

### 阶段 4：遥测数据、事件和查询

- 设备属性、遥测、事件、数据校验和持久化。
- 设计时间戳来源、数据类型、批量写入和查询分页。
- 评估关系型数据库、时序数据库或其他存储，不得仅因“物联网项目”就默认引入时序数据库。
- 明确热数据、历史数据、数据保留、数据丢失和重复写入策略。

### 阶段 5：WebSocket 实时通信

- 推送设备状态、遥测、事件和告警。
- 连接认证、租户和资源权限校验。
- 连接管理、订阅管理、断线重连和背压。
- 先实现后端协议和测试，不实现 UI。

多实例部署时必须明确连接粘性、跨实例推送、订阅状态共享和断线重连策略；不能假设任何实例都能直接访问另一实例的内存连接。

### 阶段 6：规则、告警和任务

- 基础规则判断、阈值告警、告警恢复和告警确认。
- 定时任务和简单设备命令编排。
- 先实现简单、明确、可测试的规则模型。
- 不要一开始实现复杂 DSL、可视化规则链或通用规则引擎。

### 阶段 7：通知

- 通知编排、通知模板、通知记录、发送状态和失败重试。
- 先实现站内或测试通道，再扩展邮件、短信或第三方通知通道。
- 通知领域的持久化放在 `roseiot-notice`，通道适配放在 `roseiot-infrastructure/notification/`。
- 验证告警到通知的端到端链路、幂等、重试、超时和敏感信息脱敏。

### 阶段 8：消息队列和异步处理

先证明同步方案的瓶颈或可靠性问题，再决定是否引入消息队列。必须说明：

- 消息队列解决的问题和没有解决的问题。
- 可靠性模型、投递语义、重复消费和消费者幂等。
- 消息顺序、失败重试、退避和死信。
- 数据库事务与消息发送的一致性，是否需要 Outbox。
- 本地开发、测试和部署成本。

### 阶段 9：gRPC 和跨进程调用

- 在领域用例和 API 语义稳定后，再定义 Protobuf 契约。
- 实现 gRPC Server/Client、认证、授权、deadline、取消、错误码和兼容策略。
- 验证 Docker Compose 多实例下的服务地址、负载均衡、连接复用和故障恢复。
- gRPC 适配器复用领域应用用例，不复制业务逻辑，也不推动提前拆分微服务。

### 阶段 10：可观测性、性能和部署

- 结构化日志、请求和消息关联 ID、指标、健康检查和必要的追踪。
- 建立可复现的基准测试和故障演练。
- 补充 Docker Compose 或其他最小部署方式。
- 只将已经被至少两个真实场景复用、边界稳定的基础设施能力抽取为 Spring Boot Starter，并为启用、禁用、配置覆盖和替换默认实现提供测试。
- 记录瓶颈、容量边界和下一步优化，而不是只添加监控依赖。

## 十二、代码、安全和测试要求

- 命名必须表达领域含义，避免无意义的 Base、Util、Helper、Manager 和 Service 堆叠。
- Controller 或协议适配层负责映射、输入边界和认证入口；业务规则、权限作用域、事务和跨组件编排放在合适的业务层。
- 领域逻辑不得依赖 MQTT Topic、HTTP Request 或具体 wire payload。
- 领域模型、领域服务和应用核心不得依赖 MyBatis Plus、JPA、PostgreSQL、gRPC Stub 或其他具体基础设施类型；领域模块的 `persistence/` 实现包不适用此条，但必须与领域核心隔离。
- 所有外部输入都必须校验，所有租户和资源作用域都必须在服务端强制校验。
- 密码、Token、设备密钥、API Key、OAuth Secret 和环境变量中的敏感值不得提交、打印或返回列表接口。
- API、数据库结构和消息格式要考虑版本兼容、演进和迁移。
- 明确事务边界、并发控制、重试、幂等、超时、背压和故障恢复策略。
- 数据库结构通过新的迁移文件修改，不改写已经共享的历史迁移。
- 纯逻辑使用单元测试；数据库、HTTP、MQTT、WebSocket 和消息队列行为使用集成测试或协议测试。
- 关键集成测试优先使用真实组件或 Testcontainers，避免用大量脆弱 Mock 掩盖集成问题。
- ArchUnit 架构测试必须在 Maven 验证流程中执行，并覆盖主要领域边界和持久化隔离规则。
- PostgreSQL、gRPC、Docker Compose 和多实例行为必须在涉及它们的阶段提供对应的集成或协议测试。
- 测试名称必须说明输入场景和可观察结果。
- 不以测试数量作为质量指标，不编写没有行为价值的测试。
