# Roseiot 路线图

本路线图是面向项目与 Agent 的建设指导文件，描述产品方向、阶段顺序、模块边界和当前
进度；它不是某个功能的 Spec，也不承诺固定日期。具体需求由 `/to-spec` 从已确认的对话
和代码库上下文整理为 GitHub Issue Spec，再据此拆解和实施。工作项、Spec 与进度均以
GitHub Issues 为跟踪入口；长期领域术语和架构决策分别维护在 `GLOSSARY.md` 与 `docs/adr/`。

## 建设原则

- 以可运行、可测试的业务闭环作为交付单位，不以技术组件数量衡量进度。
- 默认采用模块化单体；只有边界和收益经过真实用例验证后才拆分模块或服务。
- 优先复用 JDK、Spring 和 PostgreSQL 能力，按已测量的问题引入新基础设施。
- 物模型是设备数据和行为的领域契约，但不提前建设通用 DSL、独立物模型服务或可视化编辑器。
- 每个阶段只实现支撑当前闭环的最小能力，不为后续阶段预留空模块和占位接口。

## 当前版本范围

平台路线为阶段 0 环境基线、阶段 1 管理模块、阶段 2 IoT 模块、阶段 3 通知模块、
阶段 4 AI 模块。当前从阶段 0 开始；AI 属于后续阶段，进入实施前须先明确具体用例。
可靠性、性能和部署验证在每个模块阶段内完成，不另设质量阶段。

路线图只跟踪模块级功能进度和阶段验收：功能状态按 `未开始`、`进行中`、`已实现`、
`已验证`记录；只有通过对应验收并附上测试、部署或性能证据后，才能标为已验证。详细
API 契约、模块接口、领域模型字段及其设计评审状态由对应模块 Spec 维护；路线图不定义
具体端点、请求响应结构或模型字段。状态应链接对应 Spec、实现位置和验证证据；没有证据
不得标为已验证。
后续候选功能只有满足表中进入条件并形成独立 Spec 后，才能进入实施计划。

Roseiot 的长期模块方向与当前路线安排如下。模块方向描述平台整体，不代表每项能力
都已进入当前版本承诺。

| 模块 / 项目 | 路线图安排 | 当前边界 |
| --- | --- | --- |
| 管理 | 阶段 1 完成管理模块功能 | 包含认证、租户、用户、角色、资源和系统设置；具体设置项进入对应 Spec |
| IoT | 阶段 2 完成 IoT 模块功能 | 在同一阶段内按设备管理、遥测、命令、规则与告警切片实施 |
| 通知 | 阶段 3 完成通知模块功能 | 从 IoT 告警的 Webhook 投递切入；暂不建设未确认的通道 |
| AI | 阶段 4 完成 AI 模块功能 | 后续阶段；具体能力须由明确场景、数据条件和独立 Spec 决定 |
| Nextboard | 随后端功能规划逐步补充独立 Admin Dashboard 页面与菜单 | 使用本地演示数据，不调用 Roseiot API，不作为后端阶段验收项 |

各阶段按可独立验证的垂直切片推进，不编写覆盖全部阶段的总规格，也不先横向铺设
全部数据表、Controller 或 Repository。公开行为、数据模型、安全边界、协议或跨模块
依赖应遵循 **Spec → Plan → 实现** 门禁。

## 交付路线

### 阶段 0：环境与工程基线

目标：搭建可重复运行和验证的本地开发环境及后端工程基线，不实现业务模块功能。

- 验证 Java、Spring Boot、Maven 及其版本组合的可获得性和兼容性；
- 建立最小可运行应用、健康检查、配置入口和测试入口；
- 形成清晰但不过度拆分的代码边界；
- 记录本地启动、测试和验证命令；
- 明确配置与凭证的加载方式，确保敏感信息不进入仓库。

建议切片：版本与依赖验证 → 最小应用结构 → 类型化配置与健康检查 → 数据库迁移
与测试入口 → 本地运行文档。阶段 0 不创建尚无用例的业务空模块。

**当前状态**：已验证。已完成 `./mvnw -B verify`、`docker compose config -q` 和本地启动检查；PostgreSQL 18/Testcontainers 集成测试通过，健康、liveness 与 readiness 端点均返回 `UP`，readiness 确认包含数据库状态。CI 工作流已配置为运行同一 `verify` 命令。

完成标志：全新环境可以按照文档启动应用、调用健康检查并运行测试。

本阶段不预留 MQTT、gRPC、消息队列、缓存、Starter 或微服务框架。

### 阶段 1：管理模块

目标：交付管理端所需的身份、租户、权限和系统设置能力。

#### 用户用例

**平台管理员**

- 作为平台管理员，我希望通过初始化接口建立首个管理员账户，以便开始受控地管理平台；初始化成功后，该接口不能再次成功执行。
- 作为平台管理员，我希望创建和管理租户，并在创建时勾选租户可用的 ACTION 范围，以便设定该租户角色可获权限的上限。
- 作为平台管理员，我希望维护 MENU 与按钮操作权限目录，并为每项权限设置稳定标识，以便统一管理导航资源和可授权操作。
- 作为平台管理员，我希望分别启用或停用 MFA 能力及其支持的认证方式，并维护各方式所需设置，以便管理平台的多因素认证策略。
- 作为平台管理员，我希望通过配置模板添加、启用或停用 OIDC Provider，并配置用户字段映射，以便管理平台可用的外部登录来源。
- 作为平台管理员，我希望查看关键操作审计，以便追溯重要管理变更。

**租户管理员**

- 作为租户管理员，我希望通过邀请将用户加入本租户，并管理邀请、用户状态和角色分配，以便控制本租户成员的访问。

**获授权的管理员**

- 作为获授权的管理员，我希望维护角色、设置角色名称并从租户可用的 ACTION 范围内配置权限，以便控制用户可执行的业务操作。

**用户**

- 作为用户，我希望安全登录并查看、续期或撤销自己的登录会话，以便掌握账户的登录状态和访问范围。
- 作为已登录用户，我希望使用当前凭证修改密码，以便主动保护账户；忘记凭证时，我希望通过账户恢复流程重设密码，以便重新获得账户访问权。
- 作为用户，我希望更新个人资料，以便保持账户信息准确。
- 作为用户，我希望更改登录邮箱并验证新邮箱，以便安全更新登录标识。
- 作为用户，我希望申请注销自己的账户，以便停止使用平台并处置个人账户信息。
- 作为用户，我希望启用、管理或停用自己的 MFA 因子，以便按需要加强账户认证。

验证覆盖认证与授权、租户归属、持久化唯一性、并发状态变化、跨租户访问和敏感信息保护。
平台不开放用户自助注册；租户用户仅通过邀请加入。首个管理员通过平台初始化接口建立，该接口仅允许一次成功初始化；接口路径、访问约束及并发安全规则由管理模块 Spec 定义。
创建租户时，平台管理员勾选该租户可用的 ACTION 范围；系统据此生成首位管理员角色，将该范围内的 ACTION 分配给该角色，并创建关联此角色的邀请。角色名称默认为“租户管理员”，可通过角色表单修改；角色名称仅用于显示，不用于授权判断。租户后续创建的角色只能从租户可用范围中选择 ACTION。用户可同时拥有多个所属租户的角色；角色分配规则和上述流程的事务边界由管理模块 Spec 定义。
用户自助操作以当前认证主体确定目标账户；邮箱变更、账户注销、MFA 的启停及注销对租户
管理连续性的影响，由管理模块 Spec 明确。用户管理自己的 MFA 因子与平台管理员启用可用
MFA 方式是两个不同用例；OIDC Provider 的启用与配置属于平台管理员职责。项目术语中菜单
资源为 `MENU`，按钮代表可授权操作 `ACTION`；两类资源都可有稳定标识，但后端 API 授权
以 `ACTION` 标识为准。租户可用 ACTION 范围限定其角色的可授权集合。MFA 与 OIDC Provider 是当前已确认的系统设置；其他系统设置及关键操作审计的具体覆盖范围，由管理模块 Spec 确认。

建议切片：系统初始化与首个管理员 → 登录、会话及用户自助账户安全 → 租户、用户和邀请 →
权限目录、租户权限范围与角色授权 → MFA/OIDC 配置及其他系统设置、管理操作审计。每个切片按 Spec → Plan → 实现推进。

**当前状态**：尚未实施。历史访谈记录提到 IAM/RBAC 和租户用户 Spec 曾交付，但对应文件当前不在仓库；开始本阶段前须重新整理并确认管理模块 Spec。

完成标志：管理端范围内的用户、租户、角色、资源、租户权限范围和已确认的系统设置均可按授权管理；平台管理员可按确认的方式配置 MFA 与 OIDC Provider；用户可完成已确认的个人资料、凭证、会话和认证安全操作；自动化验证覆盖认证、授权和租户边界。

产品、设备、设备凭证和 IoT 数据能力属于阶段 2，不纳入本阶段。

#### 设计归属

本阶段具体功能规则、认证/授权边界、API 与服务接口契约、领域模型字段及其约束，均在
管理模块 Spec 中设计并评审；本路线图只记录阶段范围、模块进度和验收结果。

### 阶段 2：IoT 模块

目标：交付从设备建档、接入、数据处理到命令和告警的 IoT 业务闭环。以下是阶段内的
有序交付切片，不是独立阶段；阶段 2 只有所有切片达到验收条件后才算完成。

#### IoT 交付切片 1：产品、设备与凭证

**租户管理员**

- 作为租户管理员，我希望管理本租户的产品并登记设备，以便建立产品、设备及租户之间的归属关系。
- 作为租户管理员，我希望启用、停用或退役设备，并签发、轮换或吊销设备凭证，以便管理设备接入生命周期。

**设备**

- 作为设备，我希望使用有效凭证接入平台，以便平台验证设备身份及其所属租户和产品。

验证：使用真实 PostgreSQL 检查唯一性、并发冲突和租户隔离。

#### IoT 交付切片 2：物模型、设备状态与遥测

**租户管理员**

- 作为租户管理员，我希望为产品定义遥测字段和上报属性，以便明确设备可上报的数据契约。

**设备**

- 作为设备，我希望通过 MQTT 按所属产品的物模型上报数据，以便平台校验、去重并保存有效数据。

**获授权用户**

- 作为获授权用户，我希望查询设备当前状态、上报属性和历史遥测，以便了解设备活动及数据变化。

验证：检查未知字段、非法值、重复、乱序、异常时间、断线重连、分页和数据保留行为。

首个演示场景使用温湿度设备。本切片不实现模型继承、复杂对象类型、模型市场、设备影子
或可视化模型编辑器。

#### IoT 交付切片 3：命令与实时反馈

**租户管理员**

- 作为租户管理员，我希望为产品定义命令及其参数约束，以便客户端按设备能力下发操作。

**获授权用户**

- 作为获授权用户，我希望创建命令并查询命令状态与结果，以便追踪设备操作是否完成。
- 作为获授权用户，我希望通过 WebSocket 接收设备状态、遥测和命令结果变化，以便及时获得实时反馈。

验证：检查设备离线、超时、取消、重连、重复命令、连接恢复、慢消费者和背压。

命令闭环须能通过 HTTP 查询，实时推送不能成为结果读取的唯一方式。本切片不实现通用
工作流、批量任务调度或跨设备命令编排。

#### IoT 交付切片 4：规则与告警

**租户管理员**

- 作为租户管理员，我希望配置针对设备或产品的单字段阈值规则，以便发现设备数据超出业务阈值的情况。

**获授权用户**

- 作为获授权用户，我希望查看、确认和跟踪告警状态，以便处理设备异常并区分告警恢复与其他结束原因。

验证：检查重复触发、告警去重、规则修订和租户授权。

本切片不建设通用 DSL、可视化规则编排、复杂事件处理或重量级规则引擎。

**当前状态**：尚未实施。

阶段完成标志：授权用户能够管理产品与设备；设备按照物模型上报并查询数据；用户可下发
并追踪命令；规则可以产生和管理告警。所有闭环都通过自动化测试和可复现演示验证。

#### 设计归属

本阶段各 IoT 切片的设备协议、HTTP/WebSocket 契约、领域模型字段、状态转换、租户隔离
和性能约束，均在对应 IoT Spec 中设计并评审；本路线图只记录模块范围、切片顺序和阶段
验收结果。

### 阶段 3：通知模块

目标：将已确认的业务事实可靠地投递给外部接收方，首个通道使用 Webhook。

#### 用户用例

**租户管理员**

- 作为租户管理员，我希望配置、启用或停用 Webhook 接收端点及签名设置，以便选择本租户告警的外部接收方。
- 作为租户管理员，我希望查询投递状态并对允许重试的投递发起重投，以便处理临时失败。

**外部通知接收系统**

- 作为外部通知接收系统，我希望收到与 IoT 告警关联且可验证签名的 Webhook，以便处理告警事件。

**运维人员**

- 作为运维人员，我希望追踪告警事实、投递尝试和最终结果，以便诊断失败并验证投递恢复。

重试、幂等、去重、SSRF 防护、秘密管理和租户授权规则由通知模块 Spec 确定。

建议切片：通知事实与端点 → 签名和投递 → 失败重试及最终状态 → SSRF 防护与手动重新投递。

完成标志：IoT 告警可以触发一个经过签名的 Webhook 通知；投递结果、重试与终态可查询，
并通过自动化测试验证失败、安全及租户边界。

本阶段不建设通用通知平台或未经需求确认的其他通知通道。

**当前状态**：尚未实施。

#### 设计归属

通知功能、Webhook 契约、跨模块告警接口、投递模型及安全/重试规则，均在通知模块 Spec
中设计并评审；本路线图只记录模块范围、交付顺序和阶段验收结果。

### 阶段 4：AI 模块（后续阶段）

目标：在存在明确业务问题、足够数据和可验证收益时，交付一个有验收依据的 AI 能力。

#### 用户用例

当前没有已确认的 AI 用户用例。阶段 4 启动前，先明确具体使用者和业务问题，再由独立
Spec 描述使用者如何使用该能力、可用数据与权限边界、非 AI 基线及可量化验收指标。

**进入条件**：出现明确场景、可用数据和可量化收益；进入阶段前形成独立 Spec。未达到
这些条件时，阶段 4 保持待启动，不预建 AI 模块、模型框架或空接口。

本阶段不预先承诺异常检测、生成式 AI 或其他具体能力；具体范围由阶段 4 Spec 决定。

#### 设计归属

AI 模块的功能、数据访问接口、领域模型和模型运行方式，须在明确场景后由阶段 4 Spec
设计并评审；当前不预设具体实现。

## 各阶段的质量与部署验收

可靠性、性能和部署验证是各模块阶段的完成条件之一，应在每个阶段内按实际风险和该模块
的运行边界完成；不要等到所有模块实现后再集中补做。阶段 4 AI 也适用相同要求。

- 建立统一关联 ID、结构化日志、指标和分层健康检查；仅在现有诊断手段不足时引入分布式追踪；
- 建立可复现基准，记录吞吐、延迟、错误率、资源消耗和测试环境；
- 覆盖进程重启、数据库故障、网络中断、重复投递和积压恢复等场景；
- 根据已发现的可靠性问题决定是否引入异步队列、Outbox、Inbox 或分布式协调；
- 明确数据备份、恢复和迁移的最小流程；
- 提供最小部署方式和运维说明；
- 验证容量边界，并记录已知限制，而不是宣称未经证明的生产规模。

验证内容包括可复现的启动与部署流程、关键故障场景、数据恢复行为，以及有固定环境、
负载、持续时间、分位延迟和错误率的性能测量。只有实际验证过的结果才能作为阶段完成
证据或性能声明。

## Spec 与实施门禁

### 使用 `/to-spec` 编写功能 Spec

路线图为 `/to-spec` 提供项目方向、模块顺序、范围边界和已确认约束；不能代替具体功能
Spec。结构与发布流程遵循 [mattpocock/skills 的 `to-spec` 技能](https://github.com/mattpocock/skills/blob/main/skills/engineering/to-spec/SKILL.md)。开始前读取 README 确认实现现状，使用 `GLOSSARY.md` 中的术语，并遵守相关 ADR。
不要把路线图中尚未实施的能力描述成现有功能，也不要从规划内容推断未确认的业务规则。

当需求、用户行为或领域决策尚未说清时，先通过 [mattpocock/skills 的 `grill-with-docs` 技能](https://github.com/mattpocock/skills/blob/main/skills/engineering/grill-with-docs/SKILL.md) 澄清并记录必要的术语和架构决策，再调用 `/to-spec` 综合已有上下文；`/to-spec` 阶段不重新采访用户。

每份 Spec 聚焦一个可独立验收的用户问题或垂直切片，使用 `/to-spec` 的结构：

1. **Problem Statement**：从用户角度描述要解决的问题；
2. **Solution**：描述用户可观察到的解决方案；
3. **User Stories**：按角色列出覆盖该切片主要路径、失败路径和权限边界的故事；
4. **Implementation Decisions**：记录已确认的模块边界与接口、技术澄清、必要架构决策、API 契约、领域模型/字段及交互；把未决项明确标出，不猜测。避免易过时的文件路径和代码片段；
5. **Testing Decisions**：说明从外部行为验证什么、涉及哪些模块、优先使用哪些现有测试 seam，以及相关测试先例；
6. **Out of Scope**：列明不属于本切片的能力；
7. **Further Notes**：记录限制、依赖和其他必要背景。

Spec 中的 API 契约须定义资源路径、方法、用途、访问与授权条件、请求/响应字段、成功状态
和重要失败语义；列表接口还需说明分页、过滤、排序与边界。遵循项目 HTTP 约束，不使用
`PATCH`、`201`、`202` 或 `204`。领域模型须说明核心实体/值对象及关系，并逐字段定义名称、
含义、类型、必填性、约束、默认值/生成规则，以及敏感性与租户归属（适用时）。跨模块
接口需说明调用方向、数据所有权、事务边界和失败处理；没有真实调用方的接口不预建。
涉及异步行为时，明确幂等身份、重试、超时、终局失败及恢复行为。

测试 seam 应优先选择最高且能验证用户可见行为的现有边界，避免为测试引入不必要的抽象；
发布前向用户说明并确认拟采用的测试 seam。若需新 seam，应一并解释原因。确认后按技能
约定将 Spec 发布到 GitHub Issue，并添加 `ready-for-agent` 标签。Spec 固定外部行为和
关键约束，不提前规定类名、包名、SQL 细节或设计模式。

Spec 确认后再进行实现拆解。每个实现切片应覆盖必要的领域逻辑、持久化、协议入口、授权、
错误处理和测试；验收证据与阶段完成状态回写到对应 Issue 和本路线图。

Java、Spring Boot、数据库迁移工具、持久化方案、MQTT Broker 和测试依赖必须在首次
使用前完成最小可运行验证，再写入项目基线。技术选择只有同时满足难以逆转、缺少背景
会令人意外且存在真实权衡时才记录 ADR。

## 后续候选功能

以下功能不是当前承诺范围。只有出现明确用户场景、验收标准和触发条件后，才进入
对应 Spec；没有真实需求时不创建占位模块。

### 物模型与设备能力

| 候选功能 | 进入条件 |
| --- | --- |
| 物模型版本、草稿与发布 | 已投产模型需要兼容演进，直接修改会破坏存量设备或历史数据解释 |
| 期望属性与设备影子 | 存在离线设备配置、状态收敛和冲突处理需求 |
| 事件定义 | 遥测和属性无法准确表达离散业务事件 |
| 枚举、数组和对象类型 | 至少一个真实设备协议需要结构化字段，简单类型无法合理表达 |
| 模型导入导出 | 多产品重复建模或外部标准模型接入造成可测量的维护成本 |
| 协议字段映射 | 多类设备协议无法直接使用统一物模型标识符 |
| SDK 或代码生成 | 已有稳定模型契约，且多个设备端或客户端重复编写适配代码 |

### 设备运营

| 候选功能 | 进入条件 |
| --- | --- |
| 设备分组、标签和批量操作 | 单设备操作已无法满足真实运营规模 |
| 批量任务和作业调度 | 出现需要进度、重试、暂停和结果汇总的长时间设备操作 |
| OTA 固件升级 | 有真实固件发布、灰度、回滚和完整性校验需求 |
| 远程配置 | 命令不足以表达需要持久化、确认和收敛的设备配置 |
| 网关、子设备和拓扑关系 | 存在真实网关代理接入或设备层级关系 |
| 设备证书与双向 TLS | 风险评估或部署环境要求强设备身份与证书生命周期管理 |

### 数据能力

| 候选功能 | 进入条件 |
| --- | --- |
| 聚合、降采样和统计查询 | 原始遥测查询无法满足已确认的分析场景或性能目标 |
| 分层存储、归档和冷热数据 | PostgreSQL 在明确保留周期和数据规模下成本或性能不可接受 |
| 数据导入导出 | 出现迁移、离线分析或合规交付需求 |
| 数据质量和异常标记 | 真实数据存在需要保留但不能直接参与业务判断的异常值 |
| 地理位置与地理围栏 | 设备位置是核心业务属性，并有明确空间查询或告警场景 |

### 集成与自动化

| 候选功能 | 进入条件 |
| --- | --- |
| 更多外部集成接口 | 现有 Webhook 和管理 API 无法满足已确认的系统集成场景 |
| 外部消息系统集成 | 已存在明确消费者、吞吐或可靠投递需求 |
| 更多设备协议适配 | 有真实设备无法通过现有接入方式连接，且协议语义已经明确 |
| 规则动作扩展 | 阈值告警之外出现可复用的真实自动化动作 |
| 第三方通知通道 | 一个通知通道无法覆盖已确认的业务触达需求 |

### 平台治理与安全

| 候选功能 | 进入条件 |
| --- | --- |
| 更细粒度角色与策略 | 当前租户内授权模型无法表达真实职责分离需求 |
| API Key 和服务账号 | 出现非交互式系统集成主体，不能复用用户或设备身份 |
| 配额、限流和用量统计 | 多租户资源竞争或成本控制问题可以被测量 |
| 审计查询与导出 | 安全调查、合规或运营流程需要检索和留存审计记录 |
| 数据删除与保留策略 | 出现合同、隐私、合规或明确成本要求 |

### 产品形态与高级能力

| 候选功能 | 进入条件 |
| --- | --- |
| 管理前端 | 随后端功能规划逐步完善独立的 Nextboard 页面与菜单；使用本地演示数据，不调用 Roseiot API，并随产品能力演进 |
| 仪表盘与可视化 | 已有稳定查询接口和明确用户决策场景 |
| 数字孪生 | 设备影子不足以表达复杂实体关系、行为和仿真需求 |
| 边缘计算 | 网络、时延、带宽或离线运行需求无法由中心服务满足 |
| 插件或扩展机制 | 至少两个独立扩展场景证明固定接口的复用价值 |

## 待验证的架构假设

以下方案是实现手段，不是产品目标。只有满足触发条件后才进入 Spec 或 ADR：

| 候选方案 | 触发条件 |
| --- | --- |
| 新增领域 Maven module | 已形成清晰数据所有权、稳定契约和独立测试边界 |
| 多实例部署 | 当前切片出现容量、可用性或故障转移需求 |
| Redis | PostgreSQL 或进程内方案无法满足已测量需求 |
| 消息队列 | 同步处理出现可复现的吞吐、解耦或可靠性问题 |
| gRPC | 存在明确外部调用方或跨进程契约，且 HTTP 等现有方式不合适 |
| Spring Boot Starter | 同一能力被至少两个真实场景复用且边界稳定 |
| 时序数据库 | PostgreSQL 在明确数据规模、保留周期和查询模式下不满足要求 |
| 独立微服务 | 模块需要独立扩缩容、故障隔离或交付，且收益超过分布式成本 |
| Kubernetes | 部署规模和运维需求证明其收益高于更简单的部署方式 |

## 阶段证据

每个已交付阶段至少保留：

- 用户可观察的端到端行为；
- 与风险匹配的单元、集成或协议测试；
- 可复现的启动、验证或演示命令及实际结果；
- 数据模型、接口或协议的关键语义；
- 从空库执行数据库迁移的验证结果；
- 已知限制、失败场景和未完成范围；
- 涉及租户资源时，对合法访问、跨租户隐藏、角色拒绝、主体停用、并发状态变化和敏感信息不泄露的验证；
- 只有在记录设备数、消息频率、消息大小、并发、硬件环境、持续时间、分位延迟和错误率后才能写入的性能与容量结论。

一个阶段完成不代表其中所有候选能力都应实现。新增范围必须服务于当前业务闭环，
否则继续保留为候选项。
