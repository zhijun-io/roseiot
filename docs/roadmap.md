# Roseiot 路线图

本路线图描述产品建设顺序和能力边界，不是已批准的实现规格，也不承诺固定日期。
每个阶段开始前，应根据真实用例确定范围、非目标、验收标准和验证方式；具体工作项
和状态放在 GitHub Issues，需要正式门禁的变更放在 `docs/sdd/`。

## 建设原则

- 以可运行、可测试的业务闭环作为交付单位，不以技术组件数量衡量进度。
- 默认采用模块化单体；只有边界和收益经过真实用例验证后才拆分模块或服务。
- 优先复用 JDK、Spring 和 PostgreSQL 能力，按已测量的问题引入新基础设施。
- 物模型是设备数据和行为的领域契约，但不提前建设通用 DSL、独立物模型服务或可视化编辑器。
- 每个阶段只实现支撑当前闭环的最小能力，不为后续阶段预留空模块和占位接口。

## 当前版本范围

当前产品主路线止于阶段 0～4：身份与设备管理、物模型与遥测、命令与实时反馈、
规则告警与 Webhook 通知。阶段 5 只验证和加固已经交付的能力，不增加新的业务范围。
后续候选功能只有满足表中进入条件并形成独立 Spec 后，才能进入实施计划。

各阶段按可独立验证的垂直切片推进，不编写覆盖全部阶段的总规格，也不先横向铺设
全部数据表、Controller 或 Repository。公开行为、数据模型、安全边界、协议或跨模块
依赖应遵循 **Spec → Plan → 实现** 门禁。

## 交付路线

### 阶段 0：最小启动

目标：建立可重复运行和验证的后端工程基线。

- 验证 Java、Spring Boot、Maven 及其版本组合的可获得性和兼容性；
- 建立最小可运行应用、健康检查、配置入口和测试入口；
- 形成清晰但不过度拆分的代码边界；
- 记录本地启动、测试和验证命令；
- 明确配置与凭证的加载方式，确保敏感信息不进入仓库。

建议切片：版本与依赖验证 → 最小应用结构 → 类型化配置与健康检查 → 数据库迁移
与测试入口 → 本地运行文档。阶段 0 不创建尚无用例的业务空模块。

完成标志：全新环境可以按照文档启动应用、调用健康检查并运行测试。

本阶段不预留 MQTT、gRPC、消息队列、缓存、Starter 或微服务框架。

### 阶段 1：身份与设备管理闭环

目标：让经过认证和授权的用户能够在租户边界内管理产品与设备。

- 建立最小用户认证、租户边界和资源授权；
- 完成产品、设备和设备凭证的创建与查询；
- 建立产品与设备的归属关系，设备继承所属产品定义的能力；
- 覆盖设备启用、禁用和退役等最小生命周期；
- 支持设备凭证的创建、轮换和吊销；
- 记录关键安全操作的审计信息；
- 使用真实 PostgreSQL 验证持久化、唯一性、并发冲突和租户隔离行为。

建议切片：系统初始化与首个系统管理员 → 登录、刷新会话、注销和账户恢复 → 租户、
用户邀请、角色与停用 → 产品与设备生命周期 → 设备凭证签发、轮换、吊销与审计。

**Spec 状态（文档，非 Issue 进度）**：IAM 认证/RBAC、固定多租户模型及租户与用户（Spec #3）已交付；首管理员初始化能力待后续 Spec；产品与设备管理尚未交付。

完成标志：可以创建租户内产品和设备、签发并撤销凭证，并证明跨租户访问被拒绝。

本阶段只建立物模型的归属边界，不实现设备数据校验、复杂角色系统或组织层级。

### 阶段 2：物模型、设备状态与遥测闭环

目标：让设备按照产品定义的数据契约上报状态和遥测，并可被可靠查询。

- 为产品建立最小物模型，区分遥测、上报属性和命令；
- 首个切片只实现遥测和上报属性定义，命令定义留到阶段 3；
- 每个字段支持稳定标识符、名称、数据类型，以及按需使用的单位和取值约束；
- 初期只支持 `boolean`、`integer`、`decimal` 和 `string` 等简单类型；
- 设备通过 MQTT 认证并上报遥测或属性；
- 根据物模型校验字段名称、数据类型和取值约束，再决定是否持久化；
- 明确未知字段、部分字段失败、模型字段修改和删除的处理语义；
- 支持按租户、设备、字段和时间范围查询遥测，并明确排序和分页行为；
- 维护设备当前上报属性、在线状态和最后活动时间；
- 覆盖重复、乱序、异常时间戳、断线重连和跨租户访问场景；
- 明确遥测数据保留和删除边界，避免默认无限增长。

建议切片：遥测与属性字段定义 → MQTT 设备认证与 Topic 授权 → 上报解析、校验、去重
与持久化 → 当前属性、在线状态与最后活动时间 → 遥测查询、分页与保留清理。先以标准
温湿度设备贯穿闭环，再验证重复、乱序、异常时间和容量边界。

完成标志：设备可以按照产品物模型上报数据，非法数据被可解释地处理，授权用户可以
查询历史遥测和当前状态。

本阶段不实现模型继承、复杂对象类型、模型市场、设备影子或可视化模型编辑器。

### 阶段 3：命令与实时反馈闭环

目标：让授权用户能够向设备发出受物模型约束的命令，并获得可追踪的结果。

- 在产品物模型中增加最小命令定义，包括命令标识符、输入参数和返回结果；
- 服务端向设备下发命令，并使用稳定请求标识关联响应；
- 支持待发送、已发送、成功、失败、超时和取消等必要状态；
- 明确重复请求、幂等、设备离线、超时、取消和重连后的处理语义；
- 提供经过授权的命令创建、状态查询和结果查询；
- 记录命令发起者及关键状态变化，满足审计需要；
- 向获授权的客户端实时推送设备状态、遥测和命令结果；
- 验证连接中断、重连、慢消费者和背压行为。

建议切片：命令定义 → 命令创建、持久状态与幂等 → MQTT 下发与设备执行结果 → 超时、
取消、断线与重试竞争 → WebSocket 认证、订阅、恢复与背压。先完成可由 HTTP 查询的
命令闭环，实时推送不能成为结果的唯一读取方式。

完成标志：用户可以下发一个物模型中已定义的命令，并观察从创建到成功、失败、超时或取消的完整生命周期。

本阶段不实现通用工作流、批量任务调度或跨设备命令编排。

### 阶段 4：规则、告警与通知闭环

目标：从设备数据产生可管理的告警，并通过一个真实通知通道完成反馈。

- 从一个可测试的阈值规则开始，消费已校验的遥测或设备状态；
- 完成告警创建、更新、结束、确认和查询，并区分条件恢复与其他结束原因；
- 明确告警去重、重复触发、严重级别、确认人和确认时间；
- 实现一个本地可验证的 Webhook 通知通道；
- 明确通知发送失败、签名、SSRF 防护、重试、去重和最终状态；
- 保留从规则输入到告警及通知结果的可追踪信息；
- 验证规则和告警操作的租户隔离与授权。

建议切片：单字段阈值规则与规则修订 → 持久求值任务 → 告警创建、结束与确认 → 通知
事实与 Webhook 端点 → 签名、重试、SSRF 防护与手动重新投递。不提前建设通用规则
引擎或通用通知平台。

完成标志：一条设备数据可以触发告警、发送 Webhook 通知，并由授权用户确认告警或
观察其因条件恢复及其他明确原因而结束。

本阶段不建设通用 DSL、可视化规则编排、复杂事件处理或重量级规则引擎。

### 阶段 5：可靠性、性能与部署

目标：使用故障实验和可复现测量证明系统在明确负载下的行为。

- 建立统一关联 ID、结构化日志、指标和分层健康检查；仅在现有诊断手段不足时引入分布式追踪；
- 建立可复现基准，记录吞吐、延迟、错误率、资源消耗和测试环境；
- 覆盖进程重启、数据库故障、网络中断、重复投递和积压恢复等场景；
- 根据已发现的可靠性问题决定是否引入异步队列、Outbox、Inbox 或分布式协调；
- 明确数据备份、恢复和迁移的最小流程；
- 提供最小部署方式和运维说明；
- 验证容量边界，并记录已知限制，而不是宣称未经证明的生产规模。

完成标志：可以在记录完整环境和参数的前提下复现实验结果，并解释主要故障模式、
容量边界和恢复方式。本阶段不增加新的业务能力。

## Spec 与实施门禁

每份 Spec 至少包含：目标、用户可观察行为、范围、非目标、领域术语、不变量、授权
矩阵、状态转换、接口契约、数据约束、失败语义、验收标准和已知限制。涉及异步工作时，
还必须明确事务边界、幂等身份、重试、超时、终局失败和恢复行为。Spec 固定外部行为
和关键约束，不提前固定类名、包名、Repository 接口、SQL 细节或设计模式。

Spec 获批后再编写 Plan。Plan 将工作拆成可独立测试和交付的垂直切片，并列出预期
修改文件、数据库迁移、测试、验证命令与风险。每个业务切片应同时完成必要的领域逻辑、
持久化、协议入口、授权、错误处理和测试。

Java、Spring Boot、数据库迁移工具、持久化方案、MQTT Broker 和测试依赖必须在首次
使用前完成最小可运行验证，再写入项目基线。技术选择只有同时满足难以逆转、缺少背景
会令人意外且存在真实权衡时才记录 ADR。

## 后续候选功能

以下功能不是当前承诺范围。只有出现明确用户场景、验收标准和触发条件后，才进入
对应 Spec；没有真实需求时不创建占位模块。

### 物模型与设备能力

| 候选功能 | 进入条件 |
| --- | --- |
| 物模型版本、草稿与发布 | 已投产模型需要兼容演进，直接修改会破坏存量设备或历史数据解释 |
| 期望属性与设备影子 | 存在离线设备配置、状态收敛和冲突处理需求 |
| 事件定义 | 遥测和属性无法准确表达离散业务事件 |
| 枚举、数组和对象类型 | 至少一个真实设备协议需要结构化字段，简单类型无法合理表达 |
| 模型导入导出 | 多产品重复建模或外部标准模型接入造成可测量的维护成本 |
| 协议字段映射 | 多类设备协议无法直接使用统一物模型标识符 |
| SDK 或代码生成 | 已有稳定模型契约，且多个设备端或客户端重复编写适配代码 |

### 设备运营

| 候选功能 | 进入条件 |
| --- | --- |
| 设备分组、标签和批量操作 | 单设备操作已无法满足真实运营规模 |
| 批量任务和作业调度 | 出现需要进度、重试、暂停和结果汇总的长时间设备操作 |
| OTA 固件升级 | 有真实固件发布、灰度、回滚和完整性校验需求 |
| 远程配置 | 命令不足以表达需要持久化、确认和收敛的设备配置 |
| 网关、子设备和拓扑关系 | 存在真实网关代理接入或设备层级关系 |
| 设备证书与双向 TLS | 风险评估或部署环境要求强设备身份与证书生命周期管理 |

### 数据能力

| 候选功能 | 进入条件 |
| --- | --- |
| 聚合、降采样和统计查询 | 原始遥测查询无法满足已确认的分析场景或性能目标 |
| 分层存储、归档和冷热数据 | PostgreSQL 在明确保留周期和数据规模下成本或性能不可接受 |
| 数据导入导出 | 出现迁移、离线分析或合规交付需求 |
| 数据质量和异常标记 | 真实数据存在需要保留但不能直接参与业务判断的异常值 |
| 地理位置与地理围栏 | 设备位置是核心业务属性，并有明确空间查询或告警场景 |

### 集成与自动化

| 候选功能 | 进入条件 |
| --- | --- |
| 更多外部集成接口 | 现有 Webhook 和管理 API 无法满足已确认的系统集成场景 |
| 外部消息系统集成 | 已存在明确消费者、吞吐或可靠投递需求 |
| 更多设备协议适配 | 有真实设备无法通过现有接入方式连接，且协议语义已经明确 |
| 规则动作扩展 | 阈值告警之外出现可复用的真实自动化动作 |
| 第三方通知通道 | 一个通知通道无法覆盖已确认的业务触达需求 |

### 平台治理与安全

| 候选功能 | 进入条件 |
| --- | --- |
| 更细粒度角色与策略 | 当前租户内授权模型无法表达真实职责分离需求 |
| API Key 和服务账号 | 出现非交互式系统集成主体，不能复用用户或设备身份 |
| 配额、限流和用量统计 | 多租户资源竞争或成本控制问题可以被测量 |
| 审计查询与导出 | 安全调查、合规或运营流程需要检索和留存审计记录 |
| 数据删除与保留策略 | 出现合同、隐私、合规或明确成本要求 |

### 产品形态与高级能力

| 候选功能 | 进入条件 |
| --- | --- |
| 管理前端 | 后端闭环稳定，且需要可演示或真实运营界面；统一放在 `ui/` |
| 仪表盘与可视化 | 已有稳定查询接口和明确用户决策场景 |
| 数字孪生 | 设备影子不足以表达复杂实体关系、行为和仿真需求 |
| 边缘计算 | 网络、时延、带宽或离线运行需求无法由中心服务满足 |
| 异常检测或 AI 能力 | 有足够真实数据、基线方法和可量化收益，不以展示模型为目的 |
| 插件或扩展机制 | 至少两个独立扩展场景证明固定接口的复用价值 |

## 待验证的架构假设

以下方案是实现手段，不是产品目标。只有满足触发条件后才进入 Spec 或 ADR：

| 候选方案 | 触发条件 |
| --- | --- |
| 新增领域 Maven module | 已形成清晰数据所有权、稳定契约和独立测试边界 |
| 多实例部署 | 当前切片出现容量、可用性或故障转移需求 |
| MyBatis Plus | 首个持久化切片证明其收益高于直接 JDBC 等方案 |
| Redis | PostgreSQL 或进程内方案无法满足已测量需求 |
| 消息队列 | 同步处理出现可复现的吞吐、解耦或可靠性问题 |
| gRPC | 存在明确外部调用方或跨进程契约，且 HTTP 等现有方式不合适 |
| Spring Boot Starter | 同一能力被至少两个真实场景复用且边界稳定 |
| 时序数据库 | PostgreSQL 在明确数据规模、保留周期和查询模式下不满足要求 |
| 独立微服务 | 模块需要独立扩缩容、故障隔离或交付，且收益超过分布式成本 |
| Kubernetes | 部署规模和运维需求证明其收益高于更简单的部署方式 |

## 阶段证据

每个已交付阶段至少保留：

- 用户可观察的端到端行为；
- 与风险匹配的单元、集成或协议测试；
- 可复现的启动、验证或演示命令及实际结果；
- 数据模型、接口或协议的关键语义；
- 从空库执行数据库迁移的验证结果；
- 已知限制、失败场景和未完成范围；
- 涉及租户资源时，对合法访问、跨租户隐藏、角色拒绝、主体停用、并发状态变化和敏感信息不泄露的验证；
- 只有在记录设备数、消息频率、消息大小、并发、硬件环境、持续时间、分位延迟和错误率后才能写入的性能与容量结论。

一个阶段完成不代表其中所有候选能力都应实现。新增范围必须服务于当前业务闭环，
否则继续保留为候选项。
